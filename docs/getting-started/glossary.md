## 0–9

429 and 529
:   A provider's "too many requests" (your limit, with `retry-after`) and "overloaded" (its capacity). Both are retried with backoff, but differently: 429 means slow down, 529 means try again or try elsewhere.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

## A

Abort guard
:   A condition, evaluated continuously, that stops the experiment and rolls the fault back: an experiment hurting users has already answered its question.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Access pattern
:   The concrete reads and writes a workload performs, with their rates and latency needs: "read one restaurant's whole menu, 4,000/s, p99 < 20 ms" is an access pattern; "store menus" is not.

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

Access token, refresh token, ID token
:   An access token is for APIs; a refresh token obtains new access tokens without the user; an ID token (OIDC) tells the **client** who signed in and is never sent to APIs.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

Acknowledge / commit
:   Telling the broker a message is done. Per message in a queue broker (`ack`, `nack`, `reject`); per partition **offset** in Kafka (everything before offset *n* is done).

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

acks, idempotence and in-flight requests
:   `acks=all` waits for all in-sync replicas. Idempotence lets the broker drop duplicates from retries, and keeps order with up to 5 requests in flight per connection.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Adapter
:   Code that connects a port to a technology. **Driving adapters** call a driving port (a REST controller, a Kafka listener, a CLI, a test). **Driven adapters** implement a driven port (JDBC repository, payment-provider client, fake).

    *Chapters [9](../architecture-patterns/ch09-hexagonal-clean-architecture.md), [17](../architecture-patterns/ch17-sidecar-ambassador-adapter.md)*

Adaptive concurrency limit
:   A limit on requests in progress that moves with observed latency: grow while answers are fast, shrink when they slow down. Little's law ties it to throughput: limit ≈ throughput × latency.

    *Chapter [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Admission control
:   A Kubernetes webhook that checks every pod before it is created: here, Kyverno verifying signatures, provenance and digests.

    *Chapters [41](../security/ch41-supply-chain-compliance.md), [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Advisory database, OSV
:   Where vulnerabilities are described per package and version range. The GitHub Advisory Database (reviewed advisories, OSV format), OSV.dev and NVD are the main sources; scanners are only as good as their database and their version matching.

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

AIMD, Vegas, Gradient
:   Three ways to move the limit. **AIMD**: +1 while healthy, ×0.9 on a drop or a too-slow answer. **Vegas**: estimate queueing from latency above the minimum seen. **Gradient2**: compare short-term latency with a long-term average.

    *Chapter [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Ambassador
:   An outbound proxy representing a remote service: the app talks to `localhost`, the ambassador handles where and how.

    *Chapter [17](../architecture-patterns/ch17-sidecar-ambassador-adapter.md)*

Anti-corruption layer (ACL)
:   A translation layer that keeps the legacy model (codes, encodings, quirks) out of the new model, in both directions.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

AOT cache
:   A JVM feature (Java 24 JEP 483, simplified in Java 25 by JEP 514) that records classes loaded and linked during a **training run** and reuses them at startup. The successor of CDS for this purpose.

    *Chapter [8](../foundations/ch08-spring-boot-4-essentials.md)*

AOT cache (JDK 24+)
:   Project Leyden's successor to CDS: a training run (`-XX:AOTCacheOutput` in JDK 25, one step) records loaded **and linked** classes and, from JDK 25, method profiles, so the JIT starts compiling sooner. Started with `-XX:AOTCache`.

    *Chapters [60](../deployment/ch60-native-images-startup.md), [76](../governance-org/ch76-serverless-microservices.md)*

API-first (spec-first)
:   The OpenAPI/AsyncAPI document is written and reviewed before the code, and the code is checked against it (generation or drift tests). The opposite, code-first, generates the document from the code.

    *Chapter [27](../communication/ch27-api-contracts.md)*

API governance
:   The rules for how APIs are designed, changed and retired, and how they are enforced. Good governance is mostly automated and explains itself, so teams don't wait on a board.

    *Chapter [71](../governance-org/ch71-api-governance.md)*

AppCDS (application class data sharing)
:   An archive of parsed, verified classes, written by a training run (`-XX:ArchiveClassesAtExit`) and mapped into memory at startup (`-XX:SharedArchiveFile`). Saves class loading, not JIT time.

    *Chapter [60](../deployment/ch60-native-images-startup.md)*

Application core
:   The domain model plus the application services that implement the driving ports. No framework, no SQL, no HTTP.

    *Chapter [9](../architecture-patterns/ch09-hexagonal-clean-architecture.md)*

Architecture decision record (ADR)
:   A short, numbered record of one decision: its context, the decision, its status (Proposed, Accepted, Deprecated, Superseded) and its consequences. Records are immutable once accepted. A changed decision is a new record that supersedes or amends the old one, whose status section links to it.

    *Chapter [73](../governance-org/ch73-adrs-fitness-functions.md)*

Async appender
:   A queue in front of a slow appender. The caller enqueues and a worker thread writes. When the queue is full, the appender either blocks the caller or drops the event. Logback also drops TRACE, DEBUG and INFO **before** the queue is full.

    *Chapter [50](../observability/ch50-structured-logging.md)*

Asynchronous assertion
:   Waiting for something that happens later: a courier being assigned, an event being processed. Either sleep a fixed time and check once, or poll until true or a timeout (Awaitility polls every 100 ms for up to 10 s by default).

    *Chapter [64](../testing/ch64-component-e2e-testing.md)*

At-least-once
:   Offsets are committed after processing, so after a crash some records are delivered again. The sink must ignore duplicates, for example with a primary key (chapter 28).

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Atomic commitment
:   Several participants either all commit or all abort. A local transaction gets it from one write-ahead log; across databases it needs a protocol.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Attached resource
:   A backing service (database, broker, cache, SMTP, payment gateway) reached through a locator in config. Local and third-party resources are treated the same way.

    *Chapter [4](../foundations/ch04-twelve-factor.md)*

Authentication and authorization
:   Authentication establishes who the caller is; authorization decides what that caller may do to which object. Most API breaches are authorization failures behind working authentication.

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Authentication and SecurityContext
:   The authenticated principal and its authorities for the current request. A resource server builds a `JwtAuthenticationToken` from a validated JWT.

    *Chapter [37](../security/ch37-spring-security-7.md)*

Authorization code flow with PKCE
:   The user signs in at the authorization server, which redirects back with a short-lived one-time code; the client redeems the code, proving with the PKCE verifier that it started the flow. The only user flow in OAuth 2.1.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

AuthorizationManager
:   The decision behind `authorizeHttpRequests` rules and method security annotations.

    *Chapter [37](../security/ch37-spring-security-7.md)*

Authorization Server
:   Spring Security's OAuth 2.1 / OpenID Connect provider: registered clients, authorization code + PKCE, client credentials, refresh, token exchange, introspection, revocation, JWKS and discovery.

    *Chapter [37](../security/ch37-spring-security-7.md)*

Autonomy
:   A service can be changed, deployed, scaled and operated **without coordinating with other teams**. The practical test is "Can we deploy this on a Tuesday afternoon without telling anyone?"

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

## B

Backpressure
:   A consumer telling a producer how much it can take. In `Flow`, the subscriber requests *n* items; the publisher may block, drop or buffer when it can't deliver.

    *Chapter [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Backup and point-in-time recovery (PITR)
:   A base backup plus every WAL segment since lets you rebuild the database as of any moment: the defence against a deleted table, a bad migration or ransomware, which replication copies faithfully.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

Backward compatible
:   New provider, old consumer: existing consumers keep working after the change. (In schema registries, "backward" is defined from the reader's side: the new schema can read data written with the old one. Read the definition each tool uses.)

    *Chapter [27](../communication/ch27-api-contracts.md)*

Baggage
:   Key-value pairs propagated with the trace (header `baggage`) for application context: tenant, experiment, priority. It goes wherever the context goes, and it is not recorded on spans unless code copies it.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

Batch and request
:   The producer groups records per partition into batches (up to `batch.size` bytes) and sends the batches for one broker together in a produce request. The broker's cost is mostly per request; its throughput is mostly per byte.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Batch and stream
:   Stream processing handles each event as it arrives, so results are seconds old. Batch processing handles accumulated data on a schedule, so results are hours old but the work is cheaper and simpler. Micro-batching (a poll at a time) sits between them.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Bin packing
:   Fitting pods' requests onto as few nodes as possible. The node count, and so the bill, follows the sum of requests and how well their shapes fit the node.

    *Chapter [70](../performance-scalability/ch70-finops.md)*

Blast radius
:   How much of the system and of its traffic an experiment can affect: one pod or all, 5% of connections or 100%, staging or production.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Blast radius and abort conditions
:   How much of the system and its users an experiment can hurt, and the rule that ends the fault early when the hypothesis breaks badly.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Blocking protocol
:   If the coordinator fails after the participants prepared, they wait (holding locks) until it recovers or someone resolves them. 2PC is blocking; three-phase commit avoids it only under assumptions (bounded delays) real networks don't give; consensus-replicated participants and coordinators (Spanner) make failure rare instead.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Blue/green
:   Two complete environments; a router or Service selector switches all traffic at once. Fast to switch and to switch back, at twice the capacity.

    *Chapter [58](../deployment/ch58-cicd-gitops.md)*

Bounded context
:   The boundary within which a domain model and its language are consistent ([ch 5](../foundations/ch05-domain-driven-design.md)). Good modules and good services both follow bounded contexts.

    *Chapters [1](../foundations/ch01-architecture-styles.md), [5](../foundations/ch05-domain-driven-design.md), [74](../governance-org/ch74-maturity-migration-roadmap.md)*

Branch by abstraction
:   Put an interface in front of the code to replace, move every caller onto it, then swap the implementation behind it with a toggle, all on trunk.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

Breaking-change diff
:   A tool such as oasdiff compares two OpenAPI documents and classifies each change as ERR (breaking), WARN or INFO, from the schema alone.

    *Chapter [63](../testing/ch63-contract-testing.md)*

Brownout
:   Partial degradation: slow or failing for some fraction of requests. Harder to detect and more damaging than a clean outage.

    *Chapters [18](../architecture-patterns/ch18-resilience-patterns.md), [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Bulkhead
:   A limit on concurrent calls: a semaphore (`Bulkhead`) or a dedicated thread pool with a queue (`ThreadPoolBulkhead`).

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Bulkhead (concurrency limit)
:   A cap on requests in progress, with immediate rejection beyond it (chapter 18). Little's law sizes it: limit ≈ target throughput × latency.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Burn rate
:   How fast the budget is being spent, relative to the pace that spends exactly all of it over the window. An error ratio of 0.1% is burn rate 1; 1.44% is 14.4, which spends 2% of a 30-day budget in an hour.

    *Chapter [51](../observability/ch51-slo-alerting.md)*

Business capability
:   Something the business *does*, independent of how: "take orders", "assign riders", "collect payments". Capabilities are stable (food delivery has always needed riders) even when processes and org charts change, which makes them good boundaries.

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

## C

Cache-aside (lazy loading)
:   The application reads the cache; on a miss it reads the database and fills the cache. The most common pattern; Spring's `@Cacheable` is cache-aside.

    *Chapter [32](../data/ch32-caching-strategies.md)*

Cache stampede (thundering herd, dog-piling)
:   Many requests miss the same key at once (expiry, eviction, deploy) and all recompute it, overloading the database exactly when it is busiest.

    *Chapter [32](../data/ch32-caching-strategies.md)*

Canary
:   The new version gets a small share of traffic. At each step, an analysis compares its error rate and latency with the stable version's and decides: continue, wait, or abort and send all traffic back.

    *Chapter [58](../deployment/ch58-cicd-gitops.md)*

Canary cohort
:   A percentage of *customers* (not requests) routed to the new system, stable across requests, so a customer never flips between old and new.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

can-i-deploy
:   A query to the broker: has this version been verified against every version of its partners in the target environment? Deployable only if all of them succeeded.

    *Chapter [63](../testing/ch63-contract-testing.md)*

Cardinality and dimensionality
:   Cardinality is how many distinct values a field has (route: 20, user ID: millions); dimensionality is how many fields there are. Metrics multiply cost by every label combination; traces and events pay per record, so they can afford high cardinality.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Cascading failure
:   A failure in one component exhausting resources in its callers, which then fail their own callers.

    *Chapters [18](../architecture-patterns/ch18-resilience-patterns.md), [42](../resilience/ch42-failure-modes.md)*

Causation id
:   The id of the message or command that directly caused this one. Correlation says *which flow*; causation says *which step led to which*.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Cell
:   A complete, independent copy of the stack serving a slice of tenants. A failure (or a bad deploy) in one cell reaches only its tenants.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

Certificate-bound access token
:   An access token carrying the SHA-256 thumbprint of the client's certificate (`cnf.x5t#S256`, RFC 8705); valid only over a connection authenticated with that certificate.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

Change coupling
:   How often two contexts change in the same commit. Code Maat's degree is shared revisions divided by the average of the two contexts' revisions.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

Change data capture (CDC)
:   Reading committed changes from the database log as a stream. Debezium does this for PostgreSQL (logical replication), MySQL (binlog), SQL Server, Oracle, MongoDB and others.

    *Chapters [15](../architecture-patterns/ch15-outbox-inbox-cdc.md), [34](../data/ch34-reporting-analytics.md)*

Channel
:   A client's logical connection to a target, managing one or more HTTP/2 connections, name resolution and load balancing. Expensive to create; shared and long-lived, like chapter 22's HTTP clients.

    *Chapter [23](../communication/ch23-grpc.md)*

Chaos engineering
:   Experimenting on a system to build confidence in its ability to withstand turbulent conditions. An experiment, not a test: it asks a question whose answer you don't know.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Circuit breaker
:   A state machine per dependency. **CLOSED**: calls pass and outcomes are recorded in a sliding window. **OPEN**: calls are refused at once. **HALF_OPEN**: a few trial calls decide between the two. Also DISABLED, FORCED_OPEN and METRICS_ONLY for operations.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Circuit breaker states
:   **Closed** (calls flow, outcomes recorded), **open** (calls fail at once for a period), **half-open** (a few trial calls decide whether to close or reopen).

    *Chapter [18](../architecture-patterns/ch18-resilience-patterns.md)*

Client credentials
:   A service obtains a token for itself, with no user involved: batch jobs, service-to-service calls not on a user's behalf.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

Closed model
:   A fixed number of virtual users, each sending its next request when the previous one returns (k6's `constant-vus`, Gatling's `constantConcurrentUsers`, JMeter thread groups). Throughput follows the service: when it slows, the users slow.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Cognitive load
:   How much a team has to hold in its heads to do its work. *Team Topologies* borrows John Sweller's split: **intrinsic** (the problem itself), **extraneous** (the environment: builds, deployments, tickets) and **germane** (the domain learning that adds value). Good platforms remove extraneous load so teams can spend their capacity on germane load.

    *Chapter [7](../foundations/ch07-conways-law-team-topologies.md)*

Cold start
:   A request that finds no idle instance waits for a new one: the platform's sandbox, the runtime's start (the JVM), the function's initialisation, then the request itself. Since August 2025, Lambda bills the INIT phase too.

    *Chapter [76](../governance-org/ch76-serverless-microservices.md)*

Command
:   A request for something to happen (`ReserveCoupon`), addressed to one receiver who may refuse. Commands on a message bus are still requests, not events; naming them as events hides coupling.

    *Chapter [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Component test
:   Tests one service as a black box through its API, with its own database real and other services replaced by stubs built from their contracts. Spotify's honeycomb calls these integration tests, and reserves "integrated tests" for tests that need another service running.

    *Chapters [61](../testing/ch61-test-strategy.md), [64](../testing/ch64-component-e2e-testing.md)*

Composition root
:   The single place that decides which adapter implements which port (here, Spring `@Configuration` classes). Everything else only knows interfaces.

    *Chapter [9](../architecture-patterns/ch09-hexagonal-clean-architecture.md)*

Compression
:   Applied per batch by the producer and stored compressed. Bigger batches compress better. The broker doesn't decompress them unless formats or codecs differ.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

ConfigMap and Secret delivery
:   They can be delivered as environment variables (read at container start), mounted files (updated by the kubelet through an atomic `..data` symlink swap), or `subPath` mounts (a single file bound at start, never updated). Spring Boot's `configtree:` reads mounted files at startup only.

    *Chapter [54](../deployment/ch54-kubernetes-for-spring.md)*

Configuration (twelve-factor sense)
:   Everything that varies between deploys: URLs, credentials, feature toggles, per-city values. **Not** configuration: wiring that's the same everywhere (which beans exist, how routes map). That belongs in code.

    *Chapter [4](../foundations/ch04-twelve-factor.md)*

Conflict
:   Two writes to the same data accepted in different places without either seeing the other (two regions, offline clients). Something must decide the result: last-writer-wins, a merge function, or a human.

    *Chapter [31](../data/ch31-data-consistency.md)*

Conformance check (scorecard)
:   An automated check of a service against a platform decision, shown per service and team in the portal. Examples are Backstage's Tech Insights, Cortex and OpsLevel.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Confused deputy
:   A component with authority (here, a tool that can read any order) acting on someone else's instructions. Text in a model's context, such as a review, a web page or an email, can carry those instructions: prompt injection.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Connection-level and request-level balancing
:   kube-proxy picks a copy when a connection opens; every request on that connection goes to the same copy. An L7 proxy, a mesh sidecar or a client-side balancer picks a copy per request.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Connection pool
:   A fixed set of open database connections shared by an instance's threads. Requests beyond the pool size wait in the application, which is cheap; connections beyond what the database can work on wait inside it, which is not.

    *Chapter [33](../data/ch33-database-scaling.md)*

Connect timeout / read timeout
:   How long to wait for a connection, and for response data. Neither has a safe default: the JDK client's request timeout is unset (infinite) unless configured.

    *Chapter [22](../communication/ch22-http-clients.md)*

Consistency token
:   Something the client carries that describes what it has seen (here, a WAL position). A server answers only from a replica that is at least that far along, or from the primary.

    *Chapter [31](../data/ch31-data-consistency.md)*

Consistent hashing
:   Nodes and keys hashed onto a ring; a key belongs to the next node clockwise. Adding a node moves only the keys it takes over. **Virtual nodes** (several points per node) even out the arcs.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Consumer-driven
:   The consumer writes the contract from its own tests, so it lists only what the consumer actually uses. The provider's obligation is the union of its consumers' contracts.

    *Chapter [63](../testing/ch63-contract-testing.md)*

Consumer-driven contract (CDC)
:   Each consumer publishes the requests it makes and the parts of responses it uses; the provider's build replays them against the real provider. Tools: Pact, Spring Cloud Contract.

    *Chapter [27](../communication/ch27-api-contracts.md)*

Consumer group
:   A set of instances sharing a subscription: each event is processed once per group, by one instance.

    *Chapter [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Consumer lag
:   How far a consumer group is behind the latest offset: the key health metric for a log consumer.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Container awareness
:   The JVM reads its cgroup's CPU quota and memory limit, and treats them as the machine's size. `-XX:ActiveProcessorCount` overrides the CPU count.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Container ergonomics
:   The JVM reads the cgroup's memory and CPU limits. By default, the heap is 25% of the memory limit (`MaxRAMPercentage`), or 50% when memory is small. G1 is chosen only on a "server-class machine": at least 2 CPUs and about 1.8 GB.

    *Chapter [53](../deployment/ch53-containerization.md)*

Container lifecycle
:   An instance `@Container` field restarts per test; a static one lives for a test class; a singleton started once (a static initialiser, or JUnit's root store) lives for the whole run; a reusable container (`withReuse(true)` and `testcontainers.reuse.enable=true`) outlives the run and is found again by a hash of its configuration.

    *Chapter [62](../testing/ch62-unit-slice-integration-tests.md)*

Context and propagation
:   Inside a process, the current span and baggage live in a `Context` bound to the thread; crossing a thread needs the context captured and restored. Between processes, propagators *inject* the context into headers and *extract* it on the other side.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

Context cache
:   Spring keeps up to 32 application contexts per JVM (`spring.test.context.cache.maxSize`), keyed by the test's configuration. Tests with identical configuration share one; every `@MockitoBean` or property difference makes a new one.

    *Chapter [62](../testing/ch62-unit-slice-integration-tests.md)*

Context map
:   A diagram of bounded contexts and the **relationships** between them: who depends on whom, and how models are translated.

    *Chapter [5](../foundations/ch05-domain-driven-design.md)*

Continuous integration and delivery
:   CI merges, tests and builds every change, producing one artifact (an image digest) with its SBOM, signature and provenance (chapter 41). Delivery promotes that same artifact through environments (chapter 55). Nothing is rebuilt for production.

    *Chapter [58](../deployment/ch58-cicd-gitops.md)*

Continuous verification
:   Experiments that run on a schedule, like tests, so a regression (a lost timeout) is found within a week instead of during an incident.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Contract
:   Everything a consumer relies on: shape, behaviour, meaning, and also performance and availability expectations.

    *Chapters [27](../communication/ch27-api-contracts.md), [63](../testing/ch63-contract-testing.md)*

Contract test
:   Tests a client against a recorded description of the other service's API (a "contract"), and, on the provider's side, the provider against the same contract. Chapter 63 covers both sides.

    *Chapter [61](../testing/ch61-test-strategy.md)*

Coordinated change
:   A commit that touches two or more deployables, so their releases have to be coordinated.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

Coordinated omission
:   A closed-model load generator "coordinates" with the service: during a stall it stops sending, so the samples that would have shown the stall are never taken. HdrHistogram's `recordValueWithExpectedInterval` adds them back.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Correlation id
:   One id shared by everything that happened because of one business request, across services, messages and days.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Correlation ID and trace ID
:   A correlation (request) ID is an application value carried in headers and the MDC. A trace ID comes from the trace context (chapter 49). The OpenTelemetry agent adds `trace_id`, `span_id` and `trace_flags` to Logback's MDC. Spring Boot's Micrometer Tracing adds `traceId` and `spanId`. Pick one name for your dashboards.

    *Chapter [50](../observability/ch50-structured-logging.md)*

CORS
:   A browser mechanism that lets a server allow pages from other origins to read its responses (`Access-Control-Allow-Origin`), with a preflight `OPTIONS` request before non-simple requests. It relaxes the same-origin policy; it never protects the server from requests.

    *Chapter [40](../security/ch40-api-security.md)*

CRaC and SnapStart
:   Checkpoint a warmed-up JVM to disk (CRaC uses CRIU) and restore it later in milliseconds. Resources such as sockets and files are closed before the checkpoint and reopened after, through `jdk.crac.Resource`. AWS Lambda SnapStart applies the same idea to functions.

    *Chapter [60](../deployment/ch60-native-images-startup.md)*

CRDT
:   A conflict-free replicated data type: replicas that have seen the same updates hold the same state, whatever order they saw them in. Counters, sets (OR-Set), registers, maps.

    *Chapter [31](../data/ch31-data-consistency.md)*

Crypto-shredding
:   Encrypting each data subject's personal data with their own key, so deleting the key erases every copy, including copies that can't be edited.

    *Chapters [41](../security/ch41-supply-chain-compliance.md), [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

CSRF and ambient credentials
:   Cross-site request forgery makes a victim's browser send a state-changing request with credentials the browser attaches automatically (cookies). Bearer tokens in an `Authorization` header are not ambient, so APIs that use only them have nothing to forge.

    *Chapter [40](../security/ch40-api-security.md)*

Cycle and layering
:   Contexts that depend on each other, directly or through others, form a cycle and can't be separated without breaking it. A **layering** orders contexts so that dependencies only point down. The **fewest edges against any layering** (a minimum feedback arc set) is how much must change before the contexts can be layered.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

## D

Data classification, data residency
:   Labels that say what data a service holds (public, internal, personal, payment) and therefore where it may live and for how long.

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Data-flow diagram (DFD)
:   The system drawn as external entities, processes, data stores and data flows, with **trust boundaries** where the level of trust changes (internet → edge, services → partners). Threats concentrate where flows cross boundaries.

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Data lake, lakehouse
:   Raw and refined data in open file formats (Parquet) on object storage; table formats (Iceberg, Delta) add transactions, schema evolution and time travel so engines can query it like a warehouse.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

DataLoader / batch loading
:   A per-request utility that collects the keys requested by many resolvers at one level and loads them in a single call, with a per-request cache. `@BatchMapping` registers one for you.

    *Chapter [24](../communication/ch24-graphql.md)*

Data mesh and data products
:   Analytical data owned by the domain team that produces it and published as a product: a documented schema, an owner, a freshness and quality objective, and a stable interface, on a shared self-serve platform.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Data model
:   How a store lets you shape data: **relational** (rows, joins, constraints), **document** (a nested value per key, e.g. JSON), **key-value** (opaque value per key), **wide-column** (rows of sparse column families, partitioned by key), **search index** (inverted index of terms to documents), **time-series** (append-mostly, ordered by time), **graph** (nodes and edges).

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

Data plane and control plane
:   The **data plane** is the proxies: Envoy in Istio, linkerd2-proxy in Linkerd, ztunnel and waypoints in ambient mode. The **control plane** discovers endpoints, issues certificates and pushes configuration (xDS) to them. This chapter writes the configuration a control plane would push.

    *Chapter [57](../deployment/ch57-service-mesh.md)*

Data residency
:   Keeping personal data in a given jurisdiction. Implemented by giving each tenant (or user) a home region and routing to it; only non-personal or aggregated data leaves.

    *Chapter [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

Dead-letter queue / topic (DLQ/DLT)
:   Where messages go when they can't be processed, with the error attached, for alerting, inspection and replay.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Deadline
:   An absolute point in time by which the caller needs an answer, sent as the `grpc-timeout` header and, in grpc-java, propagated to calls the server makes while handling the request.

    *Chapters [23](../communication/ch23-grpc.md), [42](../resilience/ch42-failure-modes.md)*

Deadline budget
:   The time the original caller will wait, carried with the request (chapter 42). Each hop's timeout is taken from what is left of it, minus a reserve for the hop's own remaining work, and capped by a per-hop ceiling.

    *Chapter [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Decentralized governance
:   Standards emerge from teams and a platform's "paved road" rather than from a central architecture board. The platform constrains *how services are run* (observability, security, deployment), not *how they are written*.

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

Decide / evolve
:   `decide(state, command) → events` checks rules and produces events without changing anything; `evolve(state, event) → state` applies one event and never fails, because the event already happened.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Decision log
:   The sequence of a system's ADRs. It answers "why is it like this?", so its order, dates and links matter as much as each record.

    *Chapter [73](../governance-org/ch73-adrs-fitness-functions.md)*

Deduplication (dedup) store
:   What a consumer remembers about processed messages (event ids), for how long. Its retention is the **dedup window**.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Defence in depth
:   Several independent controls, so one failing doesn't expose the asset: the gateway authenticates, the service authorizes, the database only accepts the service's credentials.

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Delivery guarantee
:   Outbox plus relay gives **at-least-once**: never lost, sometimes duplicated. **Effectively once** processing comes from at-least-once delivery plus an idempotent consumer.

    *Chapter [15](../architecture-patterns/ch15-outbox-inbox-cdc.md)*

Delivery semantics
:   **At-most-once**: may lose, never duplicates. **At-least-once**: never loses (with retries), may duplicate. **Exactly-once**: no network can deliver exactly once across failures; what systems offer is *exactly-once effects*, meaning at-least-once delivery plus deduplication.

    *Chapters [3](../foundations/ch03-distributed-systems-fundamentals.md), [25](../communication/ch25-asynchronous-messaging.md)*

Dependency rule
:   Source-code dependencies point **inward**. Adapters depend on the core; the core depends on nothing outside itself. The driven side achieves this through **dependency inversion**: the core defines the interface, the adapter implements it.

    *Chapter [9](../architecture-patterns/ch09-hexagonal-clean-architecture.md)*

Deployable (deployment unit)
:   Something you build, version and release on its own: a JAR, a container image.

    *Chapter [1](../foundations/ch01-architecture-styles.md)*

Deprecation and sunset
:   A deprecated operation still works but should no longer be used; its sunset is when it stops working. RFC 9745's `Deprecation` header carries the date it was deprecated, RFC 8594's `Sunset` the removal date, and a `Link` points to the migration guide.

    *Chapter [71](../governance-org/ch71-api-governance.md)*

Derived store / read model
:   A copy shaped for one kind of read: a search index, a cache, a denormalised document. It lags the source and must be kept in sync (chapter 13).

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

Design for failure
:   Every remote call has a timeout. Transient failures are retried with backoff and jitter, only when safe. Concurrency is bounded. Each dependency has a defined **degradation mode**.

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

Discovery
:   **Client-side**: the caller asks the registry (usually through a local cache) and picks an instance itself (Eureka + Spring Cloud LoadBalancer, gRPC with a headless Service). **Server-side**: the caller sends to a stable address and something in between picks the instance (Kubernetes ClusterIP via kube-proxy, a cloud load balancer, a mesh sidecar).

    *Chapter [11](../architecture-patterns/ch11-service-discovery-patterns.md)*

Disposable process
:   A process that starts quickly, shuts down gracefully on SIGTERM, and is robust against sudden death.

    *Chapter [4](../foundations/ch04-twelve-factor.md)*

Domain
:   The business area the software serves: food delivery.

    *Chapter [5](../foundations/ch05-domain-driven-design.md)*

Domain event vs integration event
:   A domain event is internal to a service's model; an integration event is a published contract for other services, designed and versioned like an API.

    *Chapter [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Downward API
:   Pod metadata (name, namespace, node, labels) and its own requests and limits, as environment variables or files. Use them for log fields, metrics tags and sizing thread pools.

    *Chapter [54](../deployment/ch54-kubernetes-for-spring.md)*

Drift and pruning
:   Drift is a difference between Git and the cluster. Self-healing reapplies Git's state. Pruning deletes objects the controller created that are no longer in Git, from an inventory of what it owns.

    *Chapter [58](../deployment/ch58-cicd-gitops.md)*

DR strategies
:   **Backup and restore** (hours), **pilot light** (data replicated, compute off), **warm standby** (a smaller copy running), **active-active** (every region serves; conflicts must be designed away).

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

Dual write
:   Updating two systems (database and broker, or two databases) without a transaction that covers both.

    *Chapters [15](../architecture-patterns/ch15-outbox-inbox-cdc.md), [29](../data/ch29-polyglot-persistence.md)*

Durability level
:   What a write survives once acknowledged: process crash, machine crash, data-centre loss. PostgreSQL's `synchronous_commit` and Redis's `appendfsync` choose it; comparisons between stores are meaningless without it.

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

Dynamic secret
:   Created on request for one client, with a lease: OpenBao's database engine creates a PostgreSQL role per pod, valid until the lease ends, and drops it on revocation.

    *Chapter [39](../security/ch39-secrets-management.md)*

## E

Encryption at rest (Kubernetes)
:   An `EncryptionConfiguration` for the API server; without it, Secrets are stored unencrypted in etcd. With KMS v2, the key-encryption key stays in a cloud KMS.

    *Chapter [39](../security/ch39-secrets-management.md)*

End-to-end (E2E) test
:   A user journey through every service, deployed together the way production is. It's the only test that sees the system as one, and the most expensive and fragile.

    *Chapter [64](../testing/ch64-component-e2e-testing.md)*

Ephemeral (preview) environment
:   A complete environment created for one pipeline run or pull request, typically a namespace, and deleted afterwards. Argo CD's ApplicationSet pull-request generator creates one per open pull request, named from its number or branch.

    *Chapter [64](../testing/ch64-component-e2e-testing.md)*

Ergonomics
:   The JVM's defaults derived from that size: the collector, heap limits, and thread counts (GC worker threads, compiler threads, the common ForkJoin pool).

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Error budget
:   1 − SLO: the failures you are allowed. For 99.9% over 30 days, that is 0.1% of requests, or 43.2 minutes of total outage. The budget is spent by incidents, deploys and experiments. When it is gone, the error budget policy says what changes.

    *Chapter [51](../observability/ch51-slo-alerting.md)*

Evacuation failure and full GC
:   When G1 has no free regions to copy live objects into, it fails the evacuation and falls back to a full, compacting, stop-the-world collection: the long pause this chapter's tuning tries to avoid.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Event
:   An immutable fact in the past tense, in domain language: `EarningCredited`, `PayoutRequested`. Not `BalanceUpdated`: that's a state change, not a business fact.

    *Chapters [13](../architecture-patterns/ch13-cqrs-event-sourcing.md), [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Event loop
:   A few threads that never block: each I/O completion runs a callback, and the request's state lives in the callback chain (`CompletableFuture`, `Mono`, `Flux`). Reactor Netty starts max(CPUs, 4) of them.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Events and wide events
:   Change events are deploys, flag flips and config changes: most incidents start with one. A wide event (or canonical log line) is one structured record per request per service, with every field that might explain it, kept unsampled.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Event store
:   Append-only storage with two guarantees: events in a stream are ordered, and an append succeeds only if the stream is at the **expected version** (optimistic concurrency). A **global position** orders all events for subscribers.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Eventual consistency
:   If writes stop, all replicas eventually agree. Says nothing about what a reader sees meanwhile, which is why it needs the guarantees below to be usable.

    *Chapter [31](../data/ch31-data-consistency.md)*

Expand and contract (parallel change)
:   Make a breaking change in steps: add the new form alongside the old, migrate consumers, then remove the old form.

    *Chapter [27](../communication/ch27-api-contracts.md)*

Expand/contract (parallel change)
:   Changing a schema in backwards-compatible steps: add the new structure, migrate data and code to it, then remove the old one, each step in its own deploy.

    *Chapter [33](../data/ch33-database-scaling.md)*

Extraction seam
:   An interface, owned by the calling module, that can be implemented in-process today and over the network tomorrow without changing the caller.

    *Chapter [1](../foundations/ch01-architecture-styles.md)*

## F

Fact and dimension
:   A fact is an event or measurement (an order with an amount); a dimension describes it (the restaurant, the city, the day). Star schemas join facts to dimensions.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Failover, fencing and split brain
:   Failover promotes a standby. Fencing first makes sure the old primary can't accept writes (power it off, cut its network, revoke its storage or credentials). Without fencing, both accept writes: split brain, two histories.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

Fan-out
:   Delivering one event to every connection interested in it, possibly spread over many server instances.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Fan-out and tail amplification
:   A request that waits for *n* parallel calls is as slow as the slowest. If each call is slow with probability *p*, the request is slow with probability 1 − (1 − *p*)ⁿ: 1% per call becomes 18% at 20 calls and 39% at 50.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Fat jar vs layered
:   A fat (uber) jar is one file with every dependency inside, so any change makes a new multi-megabyte layer. A layered image puts dependencies and application classes in separate layers. Spring Boot's `-Djarmode=tools extract --layers` and Jib both do this.

    *Chapter [53](../deployment/ch53-containerization.md)*

Fault fidelity
:   How closely the injected fault behaves like the real one. A fault that is easier to handle than the real one gives false confidence.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Federation
:   One supergraph composed from **subgraphs** owned by different services, with a **router** that plans each query across them.

    *Chapter [24](../communication/ch24-graphql.md)*

First-token and idle deadlines
:   Deadlines that watch a stream: one for the first token, one for each gap between chunks. A total deadline alone can't tell a long answer from a stalled one.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Fitness function
:   An automated check that a system still has an architectural property (layering, dependency direction, latency budget). Principles become fitness functions when they fail the build.

    *Chapters [2](../foundations/ch02-characteristics-principles.md), [65](../testing/ch65-performance-chaos-arch-tests.md), [73](../governance-org/ch73-adrs-fitness-functions.md)*

Fixed and sliding windows
:   A fixed window counts requests per calendar minute and resets at the boundary; a sliding window counter blends the previous window's count into the current one.

    *Chapter [40](../security/ch40-api-security.md)*

Forward compatible
:   Old provider, new consumer: a consumer built for the new version works against the old provider (or, for data, the old schema can read data written with the new one).

    *Chapter [27](../communication/ch27-api-contracts.md)*

Four RPC types
:   **Unary** (one request, one response); **server streaming** (one request, many responses: `WatchOrder`); **client streaming** (many requests, one response: uploading GPS points); **bidirectional** (both sides stream independently: chat, live dispatch).

    *Chapter [23](../communication/ch23-grpc.md)*

Freezing
:   Recording a rule's existing violations and failing only on new ones, so a rule can be introduced into a codebase that doesn't yet satisfy it.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Freshness
:   How far behind its sources a report is. A reporting store is always behind; the question is by how much, and whether the report says so.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Function as a service (FaaS)
:   The platform runs a function per event, creating instances on demand. Each instance handles one request at a time on Lambda, and is reclaimed after an idle period the platform chooses. Billing is per request and per millisecond of execution, scaled by memory.

    *Chapter [76](../governance-org/ch76-serverless-microservices.md)*

Functions versus containers
:   A function platform runs one request per instance (by default), starts instances on demand, bills by the millisecond, and reclaims idle instances, so idle costs nothing and a cold start costs latency. Containers run all the time, or follow load more slowly, and bill for the time they exist.

    *Chapter [59](../deployment/ch59-cloud-native-platforms.md)*

## G

Game day
:   A planned session in which a team runs experiments together, with observers, a runbook and a stop button, to practise both the system's response and the people's.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Gateway aggregation
:   One client request becomes several backend calls whose results are combined. Useful, but it is the start of a slippery slope: aggregation is better done in a BFF, where it belongs to the client team.

    *Chapter [10](../architecture-patterns/ch10-api-gateway-bff.md)*

Gateway offloading
:   Cross-cutting work done once at the edge instead of in every service: TLS termination, authentication (validating tokens), rate limiting, request ids, request size limits, CORS, compression, header hygiene.

    *Chapter [10](../architecture-patterns/ch10-api-gateway-bff.md)*

Gateway routing
:   One public host and path space; the gateway forwards each request to the right service. Services can move, split and merge behind it without clients noticing.

    *Chapter [10](../architecture-patterns/ch10-api-gateway-bff.md)*

GitOps
:   The desired state of each environment lives in Git, declaratively. An agent in the cluster pulls it and reconciles continuously: it applies changes, and puts back anything that drifted. Deploys are commits; rollbacks are reverts; the Git log is the audit trail. CI never holds cluster credentials.

    *Chapter [58](../deployment/ch58-cicd-gitops.md)*

Golden path (paved road)
:   The supported way to do a common task, from creating a service to adding a database, with good defaults built in. It's optional but much easier than the alternatives; leaving it is allowed, and the team that leaves owns what it takes on.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Goodput
:   Requests completed in time to be useful, as opposed to throughput (requests completed). Under overload a server can be 100% busy with 0% goodput.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

Graceful shutdown and drain
:   On SIGTERM: report REFUSING_TRAFFIC, keep serving while Kubernetes updates endpoints, then stop accepting connections and finish in-flight requests. Spring Boot does the first and last steps; the middle one is a `preStop` sleep or a delay.

    *Chapter [52](../observability/ch52-health-checks-actuator.md)*

GrantedAuthority
:   A string the rules test: by convention `SCOPE_orders:read` for scopes, `ROLE_SUPPORT` for roles (`hasRole("SUPPORT")` checks `ROLE_SUPPORT`).

    *Chapter [37](../security/ch37-spring-security-7.md)*

Gray failure
:   A component that is degraded for some requests but passes its health checks: a disk with slow sectors, a noisy neighbour, a bad NIC queue.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

Group
:   A set of HTTP service interfaces sharing one configured client: base URL, timeouts, error handling, interceptors. Declared with `@ImportHttpServices(group = …)`, configured with `spring.http.serviceclient.<group>.*` and an `…HttpServiceGroupConfigurer` bean.

    *Chapter [22](../communication/ch22-http-clients.md)*

Guard
:   An automated check on the new path's error rate (or latency, or business metrics) that rolls back without waiting for a human.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

## H

Head and tail sampling
:   Head sampling decides at the start of a trace, by trace ID, before anyone knows how it will go. Tail sampling decides after the whole trace has been seen, so it can keep every error and every slow request.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Health
:   Whether an instance should receive traffic. Liveness (should it be restarted?) is different from **readiness** (should it get requests now?). Discovery must follow readiness.

    *Chapter [11](../architecture-patterns/ch11-service-discovery-patterns.md)*

Heartbeat
:   A small message sent on an idle connection (an SSE comment line, a WebSocket ping) so that proxies and load balancers with idle timeouts don't close it, and so either side notices a dead peer.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Hedge
:   Resilience4j's newest module: start a second attempt if the first is slow and take whichever answers first (chapter 44).

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Hedged request
:   A second, identical request sent when the first hasn't answered after a delay (typically the dependency's p95); the first answer wins. For idempotent reads only.

    *Chapters [44](../resilience/ch44-timeouts-retries-backpressure.md), [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Helm chart, values and release
:   A chart is a directory of Go templates with defaults in `values.yaml`. `helm upgrade --install` renders it with per-environment values and applies the result as a numbered **release revision**. Releases have history, `helm rollback`, and hooks.

    *Chapter [55](../deployment/ch55-helm-kustomize.md)*

Heuristic decision
:   An operator or a resource committing or rolling back an in-doubt transaction without the coordinator's decision. It unblocks the rows, and risks the participants disagreeing ("heuristic mixed").

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Hot key
:   A key that carries far more traffic than average: a popular restaurant, a celebrity account. Hashing can't spread a single key, so the hot key's partition stays hot.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

HTTP service client
:   An interface annotated with `@HttpExchange`/`@GetExchange`; Spring generates the implementation on top of a RestClient (or WebClient).

    *Chapter [22](../communication/ch22-http-clients.md)*

Hypothesis
:   A prediction that the steady state will hold under a specific fault. If it holds, confidence grows; if it breaks, you have found a weakness before your users did.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

## I

Idempotency key
:   A unique value chosen by the client per logical operation (not per attempt) and sent with every retry. The server remembers the key, a fingerprint of the request and the response.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Idempotent operation
:   An operation where applying it several times has the same effect as applying it once. `SET status = PREPARING` is idempotent; `balance = balance - 100` is not.

    *Chapters [3](../foundations/ch03-distributed-systems-fundamentals.md), [28](../communication/ch28-idempotency-correlation.md)*

Idempotent participant
:   Repeating a request with the same key (saga id + step) has no extra effect and returns the original outcome.

    *Chapter [14](../architecture-patterns/ch14-saga-pattern.md)*

Import coupling
:   One edge per source file per imported class from another context. It's a floor: references by string (configuration, reflection) aren't counted.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

Inbox (idempotent consumer)
:   A table in the consumer's database recording processed message ids, written in the same transaction as the consumer's effect.

    *Chapter [15](../architecture-patterns/ch15-outbox-inbox-cdc.md)*

Incremental aggregate
:   A summary kept current by applying each change's effect (a delta) instead of recomputing.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Independent deployability
:   The concrete, testable form of autonomy. It needs backward-compatible contracts, owned data and no shared runtime state.

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

Input validation
:   Checking that each value is what the endpoint expects (type, length, range, format, allowed fields) before it is used. It prevents bad data and narrows the attack surface; it does not replace parameterised queries or output encoding.

    *Chapter [40](../security/ch40-api-security.md)*

Integration test
:   Tests code against a real dependency it talks to: here, the repository against a database. Against an in-memory stand-in (H2) or the real engine (PostgreSQL in a container, chapter 62).

    *Chapter [61](../testing/ch61-test-strategy.md)*

Interceptor
:   Code that wraps every call on the client or server: logging, authentication, metrics, tracing. The gRPC counterpart of a servlet filter.

    *Chapter [23](../communication/ch23-grpc.md)*

Internal developer platform (IDP)
:   The self-service tools, templates and infrastructure a platform team provides so stream-aligned teams can build and run services without tickets. Its success is measured by adoption and by its users' lead time.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Introspection
:   Queries about the schema itself (`__schema`, `__type`), used by tools such as GraphiQL and code generators.

    *Chapter [24](../communication/ch24-graphql.md)*

Invalidation
:   Removing or replacing a cache entry when the source changes. "There are only two hard things in computer science": this is one.

    *Chapter [32](../data/ch32-caching-strategies.md)*

Inverse Conway maneuver
:   Design the team structure to match the architecture you want, so Conway's Law works for you. In practice the two change **together**: a reorganisation that leaves a shared database in place gets pulled back to the old shape.

    *Chapter [7](../foundations/ch07-conways-law-team-topologies.md)*

## J

jlink and jdeps
:   jdeps lists the JDK modules an application and its jars use. jlink builds a runtime containing only those modules: no compiler, no jmods, no tools you didn't ask for.

    *Chapter [53](../deployment/ch53-containerization.md)*

JWT and opaque tokens
:   A JWT carries signed claims that resource servers verify locally with the issuer's public keys; an opaque token is a reference that resource servers must **introspect** at the authorization server (RFC 7662).

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

JwtDecoder and validators
:   Decode and verify a JWT. Spring Boot builds one from `issuer-uri` (discovery, JWKS, issuer check), `audiences` and `jws-algorithms`.

    *Chapter [37](../security/ch37-spring-security-7.md)*

## K

Keep-alive
:   How long an idle instance survives. It's fixed by the platform: on Lambda it's undocumented and varies.

    *Chapter [76](../governance-org/ch76-serverless-microservices.md)*

Key-value pairs
:   SLF4J 2's fluent API, `log.atInfo().addKeyValue("order.id", id).log(...)`, attaches fields to one event without touching the MDC.

    *Chapter [50](../observability/ch50-structured-logging.md)*

kustomize base and overlay
:   A base is plain, valid YAML. An overlay lists the base and applies patches, a namespace, name prefixes, image overrides and generators. `kustomize build` (or `kubectl apply -k`) prints the result. There's no template language and no release record.

    *Chapter [55](../deployment/ch55-helm-kustomize.md)*

## L

Lack of isolation
:   Other transactions can see a saga's intermediate states (coupon reserved, order not yet approved). The **ACD** without the I: sagas are atomic (eventually), consistent and durable, but not isolated.

    *Chapter [14](../architecture-patterns/ch14-saga-pattern.md)*

Latency budget
:   An endpoint's latency objective divided among the things it waits for. The quote's objective is a p99 under 500 ms; three sequential calls of about 50 ms spend 150 ms of it before any queueing, GC or network.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Layer
:   A tar archive of filesystem changes, addressed by its digest. A registry stores each layer once, and a node pulls only the layers it lacks. Order layers from least to most often changed, and an ordinary commit changes only the last one.

    *Chapter [53](../deployment/ch53-containerization.md)*

Lease
:   A token handed out on a miss, invalidated by any write to the key; the reader's later fill is accepted only if its lease is still valid (Facebook's memcache).

    *Chapter [32](../data/ch32-caching-strategies.md)*

Lease, TTL, max_ttl
:   Every dynamic secret has a lease: renewable up to `max_ttl`, after which it ends regardless. Renewal extends; it never extends past max_ttl.

    *Chapter [39](../security/ch39-secrets-management.md)*

Least privilege, deny by default
:   Every identity gets only what it needs; anything not explicitly allowed is refused (a new endpoint is protected until someone deliberately makes it public).

    *Chapter [35](../security/ch35-security-fundamentals.md)*

linger.ms
:   How long a partition's batch waits for more records before it may be sent. 0 sends at once, but records still batch while earlier requests are in flight; Kafka 4's default is 5 ms.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Little's law
:   Requests in the system = throughput × time in the system. With 256 concurrent requests and 7,000 transactions per second, each request spends about 37 ms, however the waiting is split between pool and database.

    *Chapter [33](../data/ch33-database-scaling.md)*

Liveness probe
:   "Is this process broken beyond repair?" After `failureThreshold` failures in a row, the kubelet kills and restarts the container. A restart fixes a deadlock or a corrupted state. It can't fix someone else's outage, and it costs a full startup.

    *Chapter [52](../observability/ch52-health-checks-actuator.md)*

Live set
:   The memory still in use after a full collection: what the heap must hold at least. The headroom above it is what the collector works with.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

LLM gateway
:   A service, or a library in front of one, that all model calls go through. It holds the provider credentials, deadlines and retries, rate and concurrency limits per feature, caching, routing between models, and the per-feature accounting of tokens and cost.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Load shedding
:   A service rejecting work it can't do in time (503) rather than queueing it.

    *Chapters [18](../architecture-patterns/ch18-resilience-patterns.md), [44](../resilience/ch44-timeouts-retries-backpressure.md)*

Lock queue
:   PostgreSQL grants table locks in order. A DDL statement waiting for a lock blocks every later request that conflicts with it, even those that don't conflict with the holder.

    *Chapter [33](../data/ch33-database-scaling.md)*

Log compaction
:   A retention mode that keeps at least the latest message per key, so the topic holds "current state per entity" and a new consumer can bootstrap from it.

    *Chapter [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Logs
:   Timestamped records of what code chose to say. As free text they are hard to query; as structured JSON with a trace ID they join everything else.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Long polling
:   The client asks; the server holds the request until there is something new (or a timeout), then the client asks again immediately. Fresh, but a full request and response per update.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Lost update
:   Two read-modify-write cycles interleave and one overwrites the other's change. The classic race inside one database.

    *Chapter [31](../data/ch31-data-consistency.md)*

## M

Managed services
:   The cloud runs the Kafka cluster, database or Kubernetes control plane: patching, failover, backups. You keep the data model, capacity, client configuration and failure handling.

    *Chapter [59](../deployment/ch59-cloud-native-platforms.md)*

Masking
:   Replacing personal data and secrets with a safe form (`a***@example.in`, `******3210`, `**** **** **** 1111`). You can do it at the source, with types that print themselves masked. You can also do it at the sink, by scanning every finished line.

    *Chapter [50](../observability/ch50-structured-logging.md)*

Matchers
:   How strictly a response is compared. With no matcher a value must equal the example. **Type** matchers accept any value of the same JSON type, and cascade to everything below. **Regex** matchers check a format. **eachLike/min** matchers accept arrays of at least N elements shaped like the example. Pact always allows keys the contract doesn't mention in responses.

    *Chapter [63](../testing/ch63-contract-testing.md)*

Materialized view
:   A query whose result is stored and refreshed on demand. In PostgreSQL a refresh recomputes everything; `CONCURRENTLY` lets reads continue during it.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Maturity model
:   Levels of capability, each with exit criteria. Useful when the criteria are measured; vague when they're self-assessed.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

MaxRAMPercentage, InitialRAMPercentage, MinRAMPercentage
:   The heap's maximum and initial size as shares of memory: 25% and 1.5625% by default. MinRAMPercentage (50%) is the maximum used instead when memory is very small.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

MDC (mapped diagnostic context)
:   A per-thread `Map<String,String>` in SLF4J. Logback copies it into each event when the event is created, and encoders write it as fields. Because it is a thread-local, it doesn't follow work to another thread, and a value left behind on a pooled thread stays there.

    *Chapter [50](../observability/ch50-structured-logging.md)*

Metastable failure
:   A state of persistent overload kept alive by the system's own reactions (retries, timeouts, cache misses, reconnects) after the trigger is gone. The system has two stable states at the same load, and a trigger pushes it from the good one to the bad one.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

MeterFilter
:   A rule applied before a meter is created: add common tags, remove or rename tags, deny meters, cap a tag's values, configure histograms.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

Meter types
:   **Counter**: only goes up (orders placed). **Gauge**: a value sampled when read (queue length). **Timer**: count, total time and max of events, optionally with a histogram. **DistributionSummary**: the same for non-time values (basket size). **LongTaskTimer**: tasks in progress and how long they have been running. **FunctionCounter/FunctionTimer**: read from an object that already counts.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

Method security
:   `@PreAuthorize` and friends on service methods, enabled by `@EnableMethodSecurity`. Expressions can call beans (`@orderAccess...`) and see method arguments (`#id`).

    *Chapter [37](../security/ch37-spring-security-7.md)*

Metrics
:   Numbers aggregated in the process (counters, gauges, histograms) and sent as time series, one per distinct combination of labels. Cheap and fast to query, ideal for alerts and SLOs; they lose the individual request.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Model Context Protocol (MCP)
:   A JSON-RPC protocol for exposing tools, resources and prompts to AI applications. Since 2026-07-28 it's stateless:
    - **No handshake.** Every request carries `io.modelcontextprotocol/protocolVersion` and the client's capabilities in `_meta`.
    - **Discovery by request.** `server/discover` advertises versions and capabilities.
    - **Headers mirror the body.** On HTTP, `Mcp-Method` and `Mcp-Name` must match it.
    - **Every result carries `resultType`.**

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Module
:   A unit of code with a **public API** and **hidden internals**, inside one deployable.

    *Chapter [1](../foundations/ch01-architecture-styles.md)*

Monitoring and observability
:   Monitoring watches known failure modes with predefined checks and dashboards. Observability is the ability to explain new, unknown failures from the system's outputs. You need both: monitoring tells you *that*, observability tells you *why*.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Multi-window, multi-burn-rate alert
:   An alert that fires when the burn rate exceeds a threshold over a long window **and** a short one. The long window (1 h) makes it significant: a real share of the budget is gone. The short window (5 min, a twelfth of the long one) makes it stop soon after the problem does. Fast burns page; slow ones open a ticket.

    *Chapter [51](../observability/ch51-slo-alerting.md)*

Mutation analysis
:   Planting a bug (a "mutant") in working code and running the tests. If a test fails, the suite "killed" the mutant. Tools such as PIT generate small mutants automatically; here, 20 realistic ones were written by hand.

    *Chapter [61](../testing/ch61-test-strategy.md)*

Mutual TLS (mTLS)
:   TLS where both sides present certificates. It authenticates the workload at the other end of the connection; it does not say what that workload may do.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

## N

Native image
:   GraalVM compiles the application and the parts of the JDK it reaches into one executable, with a heap snapshot taken at build time. No class loading or JIT at runtime. Reflection, resources and dynamic proxies must be declared, usually recorded by the native-image agent.

    *Chapter [60](../deployment/ch60-native-images-startup.md)*

Native memory
:   Everything the process holds outside the heap. Native Memory Tracking (`-XX:NativeMemoryTracking=summary`) reports it by category.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Native sidecar container
:   An init container with `restartPolicy: Always`: it starts before the app containers (and can gate them with a startup probe), keeps running, is restarted if it exits, and is stopped **after** the app containers on shutdown.

    *Chapter [17](../architecture-patterns/ch17-sidecar-ambassador-adapter.md)*

Natural idempotency
:   Making the operation itself safe to repeat: set instead of increment, upsert by key, "apply only if the version is newer".

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Network partition
:   A set of nodes that can't communicate with another set, while both sets keep running and serving their own clients.

    *Chapter [3](../foundations/ch03-distributed-systems-fundamentals.md)*

Noisy neighbour
:   One tenant whose load degrades others on shared infrastructure. Limits keyed by tenant (and by client within a tenant) contain it.

    *Chapters [40](../security/ch40-api-security.md), [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

NullAway
:   An Error Prone plugin from Uber that fails the build when code can dereference a possible `null`. In JSpecify mode it understands the annotations above, including Spring's.

    *Chapter [8](../foundations/ch08-spring-boot-4-essentials.md)*

## O

Object, property and function level authorization
:   May this caller act on **this order** (BOLA, API1)? Read or change **this field** (BOPLA, API3)? Call **this operation at all** (BFLA, API5)?

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Observation API
:   One instrumentation point (`Observation`) with low-cardinality key values (become metric tags and span attributes) and high-cardinality key values (span attributes only). Handlers turn it into a timer, a span, log lines.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

OLTP and OLAP
:   Online transaction processing: many small reads and writes of current state (place an order). Online analytical processing: few large reads over history (revenue per city per month). They want different storage, indexes and isolation, and they hurt each other on the same database.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

OOMKilled
:   The kernel killing the process because the container exceeded its memory limit (exit code 137). Unlike `OutOfMemoryError`, the JVM has no say and leaves no stack trace.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Open model
:   Requests arrive at a rate regardless of earlier ones, the way independent users do (k6's `constant-arrival-rate`, Gatling's `constantUsersPerSec`). Latency is measured from when each request was due.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Ordering scope
:   Kafka orders messages **within a partition**; with a key, all messages for that key go to one partition. A queue with competing consumers has no useful ordering guarantee once more than one consumer processes in parallel.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Origin, same-origin, same-site
:   An origin is scheme + host + port (`https://www.foodfleet.in`). A *site* is the scheme and registrable domain (`https://foodfleet.in`), so `www.foodfleet.in` and `reviews.foodfleet.in` are different origins but the same site.

    *Chapter [40](../security/ch40-api-security.md)*

Other autoscalers
:   **KEDA** scales on event sources (queue length, Kafka lag, cron) and can scale to zero. **VPA** recommends or sets requests. The **cluster autoscaler** and **Karpenter** add nodes when pods can't be scheduled.

    *Chapter [56](../deployment/ch56-autoscaling.md)*

Outbox events
:   Changes the service publishes deliberately, in its own vocabulary and versioned like an API (chapter 15). The better default for data other teams depend on.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Outlier detection
:   Passive health checking: a proxy that sees an endpoint fail N times in a row ejects it from its balancing for a while, without asking the endpoint. Combined with retries on another endpoint, one bad pod stops costing anything.

    *Chapter [57](../deployment/ch57-service-mesh.md)*

## P

Partial failure
:   Some components fail while others keep working. The defining property of distributed systems, and the reason a remote call has three outcomes: success, failure, and **unknown**.

    *Chapters [3](../foundations/ch03-distributed-systems-fundamentals.md), [42](../resilience/ch42-failure-modes.md)*

Partitioning
:   Splitting one table into pieces inside one database (by range, list or hash) so queries and maintenance touch only some of them (chapter 29).

    *Chapter [33](../data/ch33-database-scaling.md)*

Partitioning (sharding)
:   Splitting data or work by key so each node owns a part. Hash partitioning spreads keys evenly; range partitioning keeps neighbours together and is prone to a hot range.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Partitions and consumer groups
:   A partition is consumed by one member of a group at a time, so a group's parallelism is at most the partition count. Extra members sit idle.

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Peer policy
:   The service's rule for which workload identities may call which routes. Deny by default.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

Percentiles and the tail
:   p50 is the typical request, p99 the slowest 1 in 100, p99.9 the slowest 1 in 1,000. The **tail** is everything above the p99. Users who make many requests meet it often.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Percentiles: client-side vs histogram
:   Client-side percentiles (`publishPercentiles`) are computed inside one process over a sliding window and published as fixed numbers: they cannot be aggregated across pods. A percentile histogram (`publishPercentileHistogram`) publishes bucket counters that Prometheus can sum across pods and turn into any percentile with `histogram_quantile`.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

Persisted queries
:   Clients send a query's hash (or ID) instead of its text; the server looks up the registered document. Smaller requests, and the server can refuse anything not registered.

    *Chapter [24](../communication/ch24-graphql.md)*

PID 1
:   The first process in the container. `docker stop` and Kubernetes send SIGTERM to it. With an exec-form entrypoint it is the JVM. With a shell form or a script it is the shell, which doesn't pass the signal on.

    *Chapter [53](../deployment/ch53-containerization.md)*

Pinning
:   A virtual thread that can't unmount while blocked, so it holds its carrier. On JDK 21, blocking inside `synchronized` pins; JDK 24 and later (JEP 491) unmount there too. Native frames still pin.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Platform thread, virtual thread, carrier
:   A platform thread is an OS thread, about 1 MB of reserved stack, and a JVM can run thousands. A virtual thread is a JVM object whose stack lives on the heap; when it blocks on I/O or `sleep`, it **unmounts** from its **carrier** (one of a few platform threads, one per CPU by default), and the carrier runs another.

    *Chapter [66](../performance-scalability/ch66-latency-virtual-threads-reactive.md)*

Pod
:   One or more containers scheduled together, sharing a network namespace (one IP, `localhost` between them) and optionally volumes.

    *Chapter [17](../architecture-patterns/ch17-sidecar-ambassador-adapter.md)*

PodDisruptionBudget (PDB)
:   It limits how many pods of a set voluntary disruptions may take down at once: drains, upgrades, the cluster autoscaler. The eviction API refuses evictions that would break it. It doesn't protect against node crashes.

    *Chapter [54](../deployment/ch54-kubernetes-for-spring.md)*

Poison message
:   A message that can never be processed (malformed, violates an invariant). Retrying it is pointless; if retried in place, it blocks everything behind it.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Poll and processing
:   `poll()` returns up to `max.poll.records` (500). What the consumer does with them decides throughput: one at a time, concurrently by key (keeping per-key order), or all at once (one database write per poll).

    *Chapter [69](../performance-scalability/ch69-kafka-throughput-tuning.md)*

Pool, bridge, silo
:   How much is shared:
    - **Pool:** shared tables with a tenant column.
    - **Bridge:** a schema per tenant in a shared database.
    - **Silo:** a database, or a whole stack, per tenant.

    Many platforms mix them: pool for most tenants, silo for the largest or most regulated.

    *Chapter [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

Port
:   An interface that belongs to the application core and is written in the core's language. **Driving** (primary, inbound) ports are what the outside world can ask the application to do: use cases such as `AuthorizePayment`. **Driven** (secondary, outbound) ports are what the application needs from the outside world: `PaymentRepository`, `PaymentGateway`.

    *Chapter [9](../architecture-patterns/ch09-hexagonal-clean-architecture.md)*

Prepared / in doubt
:   A participant that voted yes and hasn't heard the decision. It may not commit or abort on its own, keeps its locks, and survives restarts in that state.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Presumed abort
:   A recovery rule: a prepared transaction with no logged decision is rolled back. The coordinator only needs to log COMMIT decisions.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Producer and consumer spans, links
:   A message's publish is a PRODUCER span; its handling a CONSUMER span. The consumer either continues the producer's trace (parent) or starts a new trace that *links* to it, which suits batches and long delays.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

Profiles
:   Samples of what the CPU (or allocator, or lock) was doing, aggregated by stack. They show *which code* used the time; JDK Flight Recorder records them continuously at low cost.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Projection
:   A function from events to a read model, run continuously from a **checkpoint**. Disposable: throw the read model away and replay to rebuild it.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Projector
:   A process that reads changes from the source of truth (an outbox table or the database's change log) and applies them to a derived store.

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

Promotion by digest
:   An image is built once, and every environment refers to it by its content digest (`@sha256:…`). Promotion is a change to the next environment's values or overlay that copies the digest staging tested. Tags are mutable pointers; digests aren't.

    *Chapter [55](../deployment/ch55-helm-kustomize.md)*

Protocol Buffers (protobuf)
:   A language-neutral schema language and binary encoding. A message is a list of fields, each identified on the wire by its **field number**, never its name.

    *Chapter [23](../communication/ch23-grpc.md)*

Provenance, SLSA
:   A signed statement of how an artifact was built: by which builder, from which source and commit, with which parameters. SLSA's build track defines levels (L1 provenance exists, L2 signed by a hosted builder, L3 hardened builder whose provenance the build can't forge).

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Provider verification
:   The provider's build replays every interaction against the running provider and checks the responses. **Provider states** ("restaurant 7's kulfi is sold out") tell the provider which test data to set up.

    *Chapter [63](../testing/ch63-contract-testing.md)*

Public and confidential clients
:   A mobile or single-page app can't keep a secret (public); a server-side application or service can (confidential) and authenticates to the token endpoint.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

purl, CPE
:   Two ways to name a component. A package URL (`pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1`) is exact and ecosystem-aware; a CPE is NVD's product identifier, coarser and often guessed, which makes CPE matching noisy.

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Pyramid, honeycomb, trophy
:   Shapes describing how many tests of each kind to write. The pyramid puts weight on unit tests, the honeycomb on component (integrated) tests, the trophy on integration tests with static analysis as a base.

    *Chapter [61](../testing/ch61-test-strategy.md)*

## Q

Query, mutation, subscription
:   Reads, writes (executed one after another), and a stream of events over WebSocket or SSE ([chapter 26](../communication/ch26-websockets-sse.md)).

    *Chapter [24](../communication/ch24-graphql.md)*

Queue broker vs log
:   A queue broker (RabbitMQ, ActiveMQ, SQS) tracks each message's state and deletes acknowledged ones. A log (Kafka, Pulsar, RabbitMQ Streams) keeps messages for a retention period; consumers track their position (**offset**) and can replay.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Queue (point-to-point)
:   Each message is delivered to one of the consumers reading the queue (**competing consumers**), then removed once acknowledged.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Quorum
:   The minimum number of replicas that must take part in an operation. With N replicas, a write quorum W and a read quorum R overlap whenever **R + W > N**.

    *Chapter [3](../foundations/ch03-distributed-systems-fundamentals.md)*

Quorum commit
:   `synchronous_standby_names = 'ANY 1 (b, c)'`: a commit waits for any one of several standbys, so losing one standby doesn't stop writes.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

## R

Ratchet (baseline)
:   Recording an existing API's findings so a build fails only on new ones (like ArchUnit's freezing in chapter 65). The baseline only shrinks.

    *Chapter [71](../governance-org/ch71-api-governance.md)*

Ratchet (relative budget)
:   A check against the last accepted value rather than a fixed limit, so things can get better but not worse.

    *Chapter [73](../governance-org/ch73-adrs-fitness-functions.md)*

Rate limiter
:   Permits per refresh period. `AtomicRateLimiter` (the default) hands out `limitForPeriod` permits per `limitRefreshPeriod` in fixed periods; callers may wait up to `timeoutDuration` for one.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Rate limit, quota, throttling
:   A rate limit caps requests per unit of time for one key (a client, a tenant, an address) and answers `429 Too Many Requests` with `Retry-After`. A quota is a larger budget (a day, a month), often contractual. Throttling slows requests down instead of refusing them.

    *Chapter [40](../security/ch40-api-security.md)*

Readiness probe
:   "Should this pod get new traffic now?" Failing removes the pod from the Service's endpoints, so new connections go elsewhere. It doesn't restart anything, and connections that are already open stay where they are.

    *Chapter [52](../observability/ch52-health-checks-actuator.md)*

Read replica
:   A copy of the primary fed by its write-ahead log; scales reads that tolerate lag (chapter 31). Writes still scale only with the primary.

    *Chapter [33](../data/ch33-database-scaling.md)*

Read-through / write-through
:   The cache sits in the path: it loads on a miss (read-through) or is updated synchronously with the database (write-through).

    *Chapter [32](../data/ch32-caching-strategies.md)*

ReDoS
:   Regular-expression denial of service: a pattern that backtracks exponentially or polynomially on crafted input, holding a thread for seconds or minutes.

    *Chapter [40](../security/ch40-api-security.md)*

RED, USE and golden signals
:   **RED** for anything that serves requests: rate, errors, duration. **USE** for anything that is a resource (CPU, heap, pools, queues): utilisation, saturation, errors. The **four golden signals** combine them: latency, traffic, errors, saturation.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

Registration
:   **Self-registration**: the instance registers itself and sends heartbeats (Eureka clients). **Third-party registration**: something else watches the instances and registers them (Kubernetes from pod readiness, Consul agents with health checks, a cloud load balancer's target groups).

    *Chapter [11](../architecture-patterns/ch11-service-discovery-patterns.md)*

Relay (message relay)
:   The component that moves outbox rows to the broker: a **polling publisher** (queries the table) or **log tailing / CDC** (reads the database's write-ahead log).

    *Chapter [15](../architecture-patterns/ch15-outbox-inbox-cdc.md)*

Release
:   An immutable combination of a build artifact and an environment's config, with its own identifier.

    *Chapter [4](../foundations/ch04-twelve-factor.md)*

Remote dependency
:   An import edge between two deployables. After extraction it becomes an API call, an event or a shared contract.

    *Chapter [74](../governance-org/ch74-maturity-migration-roadmap.md)*

Rendezvous and jump hashing
:   Rendezvous: every node scores the key, and the highest score wins (O(n) per lookup). Jump: a formula that maps a key to one of n numbered buckets with no state, but buckets can only be added or removed at the end.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Replica
:   A copy of data on another node, kept for availability, durability or read scaling.

    *Chapter [3](../foundations/ch03-distributed-systems-fundamentals.md)*

Replication lag
:   How far a replica is behind the primary: in bytes of WAL, or in time. Asynchronous replicas are always somewhat behind and can fall far behind (long queries, network, load).

    *Chapter [31](../data/ch31-data-consistency.md)*

Replication slot
:   The source's bookmark for one CDC consumer: the source keeps every WAL segment the consumer hasn't confirmed. A consumer that stops makes the source's disk fill up.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Reporting store (read model)
:   A database owned by a reporting service, built from other services' data and shaped for queries. No other service writes to it; it can always be rebuilt from the sources.

    *Chapter [34](../data/ch34-reporting-analytics.md)*

Request factory
:   The engine underneath RestClient. Spring Boot picks one from the classpath (Apache HttpClient 5, Jetty, Reactor Netty, then the JDK's `HttpClient`); all pool connections.

    *Chapter [22](../communication/ch22-http-clients.md)*

Request fingerprint
:   A hash of the meaningful request content, stored with the key, so a key reused for a *different* request is rejected (422) instead of silently returning the wrong response.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Requests and limits
:   A request is what the scheduler reserves on a node, and the CPU share the pod gets under contention. A CPU limit is a CFS quota: at most that much CPU time per 100 ms period. When the quota is spent, the container waits for the next period: that wait is throttling. A memory limit is a hard ceiling; past it the container is OOMKilled.

    *Chapters [54](../deployment/ch54-kubernetes-for-spring.md), [70](../performance-scalability/ch70-finops.md)*

Resolver (data fetcher)
:   The code that produces one field's value for one parent object. In Spring for GraphQL, `@QueryMapping`, `@SchemaMapping` and `@BatchMapping` methods; fields without one are read from the parent object's properties.

    *Chapter [24](../communication/ch24-graphql.md)*

Resource and semantic conventions
:   The resource describes *who* is reporting (service.name, service.version, service.instance.id); semantic conventions fix attribute names (http.route, http.response.status_code) so every service and tool agrees.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Resource owner, client, authorization server, resource server
:   The user; the application acting for them; the server that authenticates users and issues tokens (Keycloak, Spring Authorization Server, Okta, Entra ID); the APIs that accept tokens (FoodFleet's services).

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

Response cache
:   Reusing an earlier answer instead of calling the model. It can match by the exact prompt, by a normalised prompt (case, punctuation, spacing), or by similarity, which is the semantic cache. Similar isn't the same: two questions can be close in words and opposite in meaning.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Retry amplification
:   Retries at several layers multiply: *k* attempts at each of *n* layers can send *kⁿ* requests to the bottom service.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

Retry and interval function
:   How many attempts (`maxAttempts`, including the first: default 3), which failures qualify, and how long to wait between them (`IntervalFunction`: fixed, exponential, randomized).

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Retry storm (retry amplification)
:   Retries multiplying load on a dependency that is failing *because* of load. Three layers each retrying three times means up to 27 calls per user request.

    *Chapter [18](../architecture-patterns/ch18-resilience-patterns.md)*

Right-sizing
:   Setting requests from measured usage. VPA's recommender takes the 90th percentile of CPU usage and of memory peaks, adds a 15% safety margin, and gives lower and upper bounds (the 50th and 95th percentiles).

    *Chapter [70](../performance-scalability/ch70-finops.md)*

Row-level security (RLS)
:   Database policies that filter every query on a table by a condition, here `tenant_id = <the current tenant>`. Superusers and `BYPASSRLS` roles always bypass it, and table owners do unless the table has `FORCE ROW LEVEL SECURITY`.

    *Chapter [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

RPO (recovery point objective)
:   How much acknowledged data may be lost in a disaster, as time or transactions. "Zero" means no commit a client was told about may disappear.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

RTO (recovery time objective)
:   How long until the service works again: detection, decision, promotion, clients finding the new primary, caches warming.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

## S

Saga
:   A sequence of local transactions, each committed on its own, with compensations for undo (chapter 14). No locks span services; intermediate states are visible.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

Saga log
:   The orchestrator's durable record of each saga's progress, written before moving on, so another instance can resume after a crash.

    *Chapter [14](../architecture-patterns/ch14-saga-pattern.md)*

SameSite, synchronizer token, Fetch Metadata
:   Three CSRF defences: a cookie attribute that withholds the cookie from cross-*site* requests; a secret token the page must echo in a header; and `Sec-Fetch-Site/Mode/Dest`, headers the browser sets to say where a request came from.

    *Chapter [40](../security/ch40-api-security.md)*

Sampling decisions
:   Made once, at the root, and carried in the sampled flag. *Parent-based* samplers follow the caller's decision; a sampler that isn't parent-based decides again and can drop half a trace or keep fragments.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

SBOM
:   A software bill of materials: every component in an artifact with its version and identity. **CycloneDX** and **SPDX** are the two formats; both are accepted by regulators (the CRA names no format).

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Scale-out limit
:   The point where more copies stop adding throughput because something they share is saturated: a database, a payment provider, a lock, a partition. The Universal Scalability Law describes the curve.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Scale to zero
:   A container platform (Knative, Cloud Run) that removes the last instance when traffic stops. Its defaults include a 60 s stable window and a 30 s grace period before the last pod goes. The first request after that waits for a cold start; others share warm instances, many requests each.

    *Chapter [76](../governance-org/ch76-serverless-microservices.md)*

Scaling and performance profile
:   Split when two parts need very different scale, latency or availability: zone lookups run on every menu browse, rider assignment once per order.

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

Scaling policies
:   Limits on the rate of change per period: by default, up by 4 pods or 100% every 15 s, whichever is more, and down by up to 100% every 15 s.

    *Chapter [56](../deployment/ch56-autoscaling.md)*

Schema (SDL)
:   The typed description of the graph: object types, fields, arguments, enums, and the root types `Query`, `Mutation` and `Subscription`. It is the contract between clients and server.

    *Chapter [24](../communication/ch24-graphql.md)*

Scopes and audience
:   Scopes are what the client may do for the user (`orders:read`); the audience is which API the token is for (`order-service`). A token without a checked audience is accepted by every API that trusts the issuer.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

Secret
:   Anything that grants access: database passwords, API keys, signing keys, client secrets, TLS private keys. A secret's risk is its **reach** (what it opens) × its **lifetime** × the **number of places** it is stored.

    *Chapter [39](../security/ch39-secrets-management.md)*

Secret zero
:   The credential needed to fetch the other secrets. Platform identity removes it: the pod's Kubernetes service-account token is exchanged for an OpenBao token (chapter 38's idea, for secrets).

    *Chapter [39](../security/ch39-secrets-management.md)*

Security and compliance boundary
:   Split to shrink an audit scope: card data in one small tokenisation service keeps the rest of the system out of PCI DSS scope.

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

SecurityFilterChain
:   An ordered list of servlet filters applied to requests matching the chain. An application can have several (the authorization server has one for its endpoints and one for login).

    *Chapter [37](../security/ch37-spring-security-7.md)*

Selection set
:   The fields a query asks for at each level. The response has exactly that shape: no more fields, no fewer.

    *Chapter [24](../communication/ch24-graphql.md)*

Semantic lock
:   An application-level marker (`PENDING` order) that tells other operations a saga is in progress on that record.

    *Chapter [14](../architecture-patterns/ch14-saga-pattern.md)*

Server-Sent Events (SSE)
:   A `text/event-stream` response that never ends. Each event has optional `id:`, `event:` and `retry:` fields and `data:` lines. Browsers' `EventSource` reconnects automatically and sends the last id in `Last-Event-ID`. Server to client only, text only.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Server-side apply (SSA)
:   The API server merges what you send into the live object and records a **field manager** for every field. Changing a field another manager owns is a **conflict**, unless you force it. Client-side apply (kubectl's default) and Helm 3 compute a patch locally from the last applied state instead, and overwrite.

    *Chapter [55](../deployment/ch55-helm-kustomize.md)*

Server-side dry run
:   Sending manifests to the Kubernetes API server with `dryRun=All`: they're validated and defaulted as if applied, but not stored.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Service
:   A deployable that owns a business capability **and its data**, reachable only through its API.

    *Chapter [1](../foundations/ch01-architecture-styles.md)*

Service and kube-proxy
:   A Service gives a stable virtual IP and DNS name. kube-proxy picks a ready pod for each new **connection**, not each request, so a connection reused for thousands of requests stays on one pod.

    *Chapter [54](../deployment/ch54-kubernetes-for-spring.md)*

Service registry
:   A database of service instances: name, address, port, metadata (zone, version), and health. Eureka, Consul, ZooKeeper, and in Kubernetes the API server's EndpointSlices.

    *Chapter [11](../architecture-patterns/ch11-service-discovery-patterns.md)*

Service, RPC, stub
:   A `.proto` `service` declares RPC methods. Code generation produces a server base class (`OrderTrackingImplBase`) to extend and client **stubs**: blocking, asynchronous and future-based.

    *Chapter [23](../communication/ch23-grpc.md)*

Service template
:   A skeleton repository with placeholders that the scaffolder fills in: application code, Dockerfile, manifests, catalog entry, API description, CI. Backstage's scaffolder runs it as a `Template` entity with steps such as `fetch:template`, `publish:github` and `catalog:register`.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Session guarantees
:   Promises to one client (a session), not to everyone: **read-your-writes** (you see your own writes), **monotonic reads** (you never see older data after newer), **monotonic writes** (your writes apply in order), **writes-follow-reads** (your write is ordered after what you had read).

    *Chapter [31](../data/ch31-data-consistency.md)*

Session state
:   Data that lives across a user's requests: a cart, a login, a wizard's progress. It belongs in a shared store (Spring Session with Redis or JDBC, a database, a signed token) for the service to stay stateless.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Shadow traffic (dark launch, mirroring)
:   The old system answers; the new one is called too and its answer compared and discarded.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

Sharding
:   Splitting data across several databases by a **shard key**. Each shard holds a subset of rows; queries that include the key go to one shard, others go to all.

    *Chapter [33](../data/ch33-database-scaling.md)*

Shared staging
:   One long-lived environment that many pipelines deploy to and test against. Its data accumulates, and its state is whatever the last test left.

    *Chapter [64](../testing/ch64-component-e2e-testing.md)*

Short polling
:   The client asks on a timer. Simple and cache-friendly, but stale by up to the interval, wasteful when nothing changes, and it misses intermediate states.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Showback and chargeback
:   Showing each team its share of the bill (showback), or billing it (chargeback). Allocation can follow requests, usage, or (OpenCost's rule) the larger of the two per container. The rest is idle and has to be shared out somehow.

    *Chapter [70](../performance-scalability/ch70-finops.md)*

Shuffle sharding
:   Each tenant gets its own small, pseudo-random subset of instances; two tenants rarely share the whole subset, so one poison tenant takes down very few others completely.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

Sidecar
:   A helper container that extends the app without the app's code knowing.

    *Chapters [17](../architecture-patterns/ch17-sidecar-ambassador-adapter.md), [57](../deployment/ch57-service-mesh.md)*

Sigstore (keyless signing)
:   The signer authenticates with OIDC (for CI, the workflow's token); Fulcio issues a certificate valid for about ten minutes naming that identity; the signature is recorded in the Rekor transparency log and/or timestamped. Verifiers check the certificate chain, the log or timestamp, and **the identity**.

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Single-flight / request coalescing
:   Concurrent misses for one key wait for one load. Per instance (a lock in memory, `@Cacheable(sync = true)`) or across instances (a lock in Redis).

    *Chapter [32](../data/ch32-caching-strategies.md)*

Single responsibility (service level)
:   A service has one reason to change: one business capability. It's the Single Responsibility Principle applied to a deployable and its team, not a rule about lines of code.

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

Sliding window
:   What the breaker judges: the last *N* calls (**COUNT_BASED**, the default, *N* = 100) or the calls in the last *N* seconds (**TIME_BASED**). Nothing is judged until `minimumNumberOfCalls` have been seen.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

SLI (service level indicator)
:   A ratio of good events to valid events, measured where users experience it. Two examples are "checkout requests that didn't fail with a server error" and "successful checkout requests completed within 300 ms". Ratios of events, not averages or percentiles, so they can be added up over any window.

    *Chapter [51](../observability/ch51-slo-alerting.md)*

SLO boundaries
:   Extra histogram buckets at exactly the latencies your objectives use (250 ms), so "share of requests within 250 ms" is a count, not an interpolation.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

SLO (service level objective)
:   A target for an SLI over a rolling window, such as 99.9% over 30 days. It is internal, and stricter than any SLA (the contract with penalties).

    *Chapter [51](../observability/ch51-slo-alerting.md)*

Slot (virtual shard)
:   A fixed number of hash buckets (4,096 here; Redis Cluster uses 16,384) mapped to physical shards. Adding a shard reassigns whole slots; keys never change slots.

    *Chapter [33](../data/ch33-database-scaling.md)*

Slow call
:   A call that succeeded but took longer than `slowCallDurationThreshold` (default **60 s**). When the share of slow calls passes `slowCallRateThreshold` (default **100%**), the breaker opens, without a single error.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Slow consumer
:   A client that can't receive as fast as events are produced (bad network, backgrounded app). The server must bound what it buffers for it.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Smart endpoints, dumb pipes
:   Logic, routing decisions and data transformation belong in the services at the ends. The pipe (HTTP, a message broker) only delivers bytes reliably.

    *Chapter [2](../foundations/ch02-characteristics-principles.md)*

Snapshot
:   A cached state at some version, so loading reads only the events after it. An optimisation, never the source of truth.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Software catalog and developer portal
:   A catalog lists every component, API, system and owning team, each described by a file kept with the code (Backstage's `catalog-info.yaml`). A developer portal (Backstage) puts documentation, ownership, API definitions and templates in one place.

    *Chapter [71](../governance-org/ch71-api-governance.md)*

Source of truth
:   The one store whose data is authoritative for a fact. Everything else holding that fact is a **derived store** (a copy, cache, read model or index) and can be rebuilt from the source.

    *Chapter [29](../data/ch29-polyglot-persistence.md)*

SPIFFE ID
:   A URI naming a workload: `spiffe://<trust-domain>/<path>`, for example `spiffe://foodfleet.internal/ns/orders/sa/order-service`. Strict syntax (lowercase trust domain, no query, no `..`), so there is one spelling per identity.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

SPIRE
:   Issues SVIDs after *attestation*: the agent proves which node it runs on (here, a Kubernetes projected service-account token), then identifies each workload by kernel and kubelet facts (namespace, service account). The workload needs no secret to get its identity.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

Spot capacity
:   Spare capacity sold at a deep discount that the provider can reclaim with short notice (two minutes on AWS). It suits work that can lose copies: stateless services above an on-demand base, batch jobs, CI.

    *Chapter [70](../performance-scalability/ch70-finops.md)*

Spring AOT
:   Build-time processing that generates bean definitions as code, required for GraalVM native images and optional on the JVM.

    *Chapter [8](../foundations/ch08-spring-boot-4-essentials.md)*

Spring Boot availability states and health groups
:   `LivenessState` (CORRECT or BROKEN) and `ReadinessState` (ACCEPTING_TRAFFIC or REFUSING_TRAFFIC) are the application's own view. They are served as `/actuator/health/liveness` and `/readiness`, which include only those states by default. `/actuator/health` aggregates every contributor (database, disk, broker) as the worst status, and that is what monitoring should read.

    *Chapter [52](../observability/ch52-health-checks-actuator.md)*

Spring Cloud CircuitBreaker
:   An API (`CircuitBreakerFactory.create("x").run(supplier, fallback)`) with Resilience4j behind it; useful when a library must not depend on Resilience4j directly.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Spring Cloud Function
:   Business logic written as `java.util.function` beans and selected by `spring.cloud.function.definition`. Adapters run the same functions on AWS Lambda (`FunctionInvoker`), Azure, or as plain web endpoints.

    *Chapter [76](../governance-org/ch76-serverless-microservices.md)*

Spring Framework 7 resilience
:   `RetryTemplate`/`RetryPolicy` in `spring-core`; `@Retryable` and `@ConcurrencyLimit` in `spring-context`, switched on by `@EnableResilientMethods`. No circuit breaker, no rate limiter.

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Stabilization window
:   The HPA remembers its recommendations. To scale down, it uses the **highest** recommendation in the window (300 s by default); to scale up, the lowest (0 s by default). A quick dip doesn't remove pods; a quick spike adds them.

    *Chapter [56](../deployment/ch56-autoscaling.md)*

Stale-while-revalidate
:   Serve the expired value while one caller refreshes it in the background.

    *Chapter [32](../data/ch32-caching-strategies.md)*

Startup probe
:   "Has it finished starting?" Until it succeeds, liveness and readiness probes don't run. It replaces a long `initialDelaySeconds`, which delays failure detection after every restart too.

    *Chapter [52](../observability/ch52-health-checks-actuator.md)*

Stateless service
:   A copy that keeps nothing between requests that another copy would need. Any copy can serve any request, so copies can be added, removed and replaced freely.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Static secret
:   Created once and stored (KV, Kubernetes Secret). Must be rotated deliberately.

    *Chapter [39](../security/ch39-secrets-management.md)*

Status code
:   The outcome of every call: `OK` or one of 16 error codes (`NOT_FOUND`, `INVALID_ARGUMENT`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`, …), sent in HTTP/2 trailers.

    *Chapter [23](../communication/ch23-grpc.md)*

Steady state
:   The system's normal behaviour, measured in what users see (success rate, latency, orders per minute), not in internals (CPU, pod count). FoodFleet's: 99% of menu requests succeed and p99 stays at or under 300 ms.

    *Chapter [45](../resilience/ch45-chaos-engineering.md)*

Steady-state hypothesis
:   A measurable statement of normal behaviour ("99% of orders succeed, p99 under 500 ms") that a chaos experiment expects to hold while a fault is injected.

    *Chapter [65](../testing/ch65-performance-chaos-arch-tests.md)*

Sticky sessions (affinity)
:   Routing a user's requests to the same copy: by cookie at an ingress, or by client address (`sessionAffinity: ClientIP`, three hours by default) at a Service. It keeps in-memory state reachable, until the copy goes away.

    *Chapter [68](../performance-scalability/ch68-horizontal-scaling.md)*

Stop-the-world pause and concurrent collection
:   Serial and Parallel stop the application for every collection. G1 stops it for copying young objects and compacting, and marks the old generation concurrently. ZGC and Shenandoah do nearly everything concurrently, with pauses well under a millisecond, using more CPU and memory to do so.

    *Chapter [67](../performance-scalability/ch67-jvm-tuning-containers.md)*

Strangler facade
:   The single place that decides, per request, whether the old or new system answers. Usually the gateway for external calls, plus an in-process switch for internal ones.

    *Chapter [16](../architecture-patterns/ch16-strangler-fig-migration.md)*

Stream
:   The ordered events of one aggregate instance (`wallet-ravi`). Its length is the aggregate's **version**.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Stream of change
:   A continuous flow of work aligned to a business area (a product, a user journey, a capability). The thing stream-aligned teams are aligned to.

    *Chapter [7](../foundations/ch07-conways-law-team-topologies.md)*

STRIDE
:   Spoofing (authenticity), Tampering (integrity), Repudiation (non-repudiation), Information disclosure (confidentiality), Denial of service (availability), Elevation of privilege (authorization). **STRIDE per element** applies only the categories that make sense for each element type.

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Strong consistency (linearizability)
:   Every read sees the latest completed write, as if there were one copy. Needs coordination on every operation: a single leader, or a quorum.

    *Chapter [31](../data/ch31-data-consistency.md)*

Structural diff
:   Comparing two versions of a schema document and classifying changes (tools: oasdiff, openapi-diff, Buf for protobuf, schema registry compatibility checks).

    *Chapter [27](../communication/ch27-api-contracts.md)*

Structured log
:   One machine-readable record per event, usually a JSON object per line, with named fields (`@timestamp`, `log.level`, `service.name`, `trace.id`, `order.id`) instead of a sentence for a regex to take apart. People still read the `message`; queries use the fields.

    *Chapter [50](../observability/ch50-structured-logging.md)*

Style guide and linting
:   A style guide states the rules with reasons; a linter checks an API's description against them. **Spectral** runs rulesets over OpenAPI and AsyncAPI documents, with severities (error, warn, info).

    *Chapter [71](../governance-org/ch71-api-governance.md)*

Subdomain
:   A part of the domain. **Core**: where you differentiate and must excel (rider dispatch, ETA prediction). **Supporting**: necessary and specific to you, but not a differentiator (restaurant onboarding). **Generic**: solved problems you should buy or reuse (identity, payments gateway, email).

    *Chapter [5](../foundations/ch05-domain-driven-design.md)*

Subdomain / bounded context
:   The DDD view from [chapter 5](../foundations/ch05-domain-driven-design.md): one model and one language per boundary. In practice capabilities and contexts usually line up; where they don't, the context boundary (where the *meaning* of words changes) wins.

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

Synchronous / asynchronous replication
:   Synchronous: a commit returns only after a standby has the change (in PostgreSQL: written, flushed or applied, per `synchronous_commit`). Asynchronous: the commit returns at once and the standby catches up; whatever it hasn't received is lost if the primary is.

    *Chapter [46](../resilience/ch46-disaster-recovery.md)*

## T

Tags and the meter ID
:   A meter is identified by its name and its tags; every distinct set of tag values is a separate meter and, in Prometheus, separate time series. Tag values must come from a small, known set.

    *Chapter [48](../observability/ch48-metrics-micrometer.md)*

Tail latency at fan-out
:   If a request fans out to *k* calls and waits for all of them, it is slow whenever any of them is slow; the probability grows with *k*.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

Team
:   A service should be owned by exactly one team, and a team should own a small number of related services. Boundaries that fight team structure lose ([chapter 7](../foundations/ch07-conways-law-team-topologies.md)).

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

Team API
:   Everything a team offers to others: its services' APIs and events, documentation, on-call contact, roadmap, and how to ask for things. A team with a clear API can be depended on without meetings.

    *Chapter [7](../foundations/ch07-conways-law-team-topologies.md)*

Technology radar
:   A team's view of technologies in four rings: **Adopt**, **Trial**, **Assess** and **Hold** (Build Your Own Radar now calls Hold "Caution"), across four quadrants. Each blip has a short rationale.

    *Chapter [73](../governance-org/ch73-adrs-fitness-functions.md)*

Template drift
:   The distance between a service and the current template. It grows two ways: the team changes the service, and the platform changes the template.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Tenant
:   A customer organisation (here, a restaurant chain) whose users and data are kept apart from other tenants on shared infrastructure.

    *Chapter [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

Tenant context
:   The current request's tenant, carried from the token to the database. In PostgreSQL that's a setting such as `app.tenant_id`, set per transaction (`SET LOCAL`), never per session.

    *Chapter [75](../governance-org/ch75-multi-tenancy-multi-region-compliance.md)*

Tenant isolation, BOLA
:   Keeping one tenant's data and load away from another's: silo (separate databases), bridge (separate schemas) or pool (shared tables with a tenant column). Broken object-level authorization (BOLA, API1:2023) is reading or changing an object by its id without checking it belongs to the caller.

    *Chapter [40](../security/ch40-api-security.md)*

Testcontainers
:   A library that starts Docker containers from tests, waits until they're ready, and removes them afterwards (with a reaper container, Ryuk, for crashed runs). `PostgreSQLContainer` runs PostgreSQL with `fsync=off`.

    *Chapter [62](../testing/ch62-unit-slice-integration-tests.md)*

Test data isolation
:   Each test creates the data it needs (its own customer, its own restaurant) instead of relying on fixtures others can consume.

    *Chapter [64](../testing/ch64-component-e2e-testing.md)*

Test isolation
:   Keeping one test's data from another's: roll back each test's transaction, truncate tables after each test, or give each test a fresh database.

    *Chapter [62](../testing/ch62-unit-slice-integration-tests.md)*

Test slice
:   A Spring Boot test that starts only the part of the application one layer needs. `@WebMvcTest` loads controllers, filters and MockMvc; `@JdbcTest` and `@DataJpaTest` load data access, run each test in a transaction rolled back at the end, and by default replace the DataSource with an embedded database unless it's already a test database (a `@ServiceConnection` container counts).

    *Chapter [62](../testing/ch62-unit-slice-integration-tests.md)*

The replica calculation
:   desired = ceil(current ratio × pods counted), where ratio = utilization ÷ target. Ratios within ±10% of 1 change nothing (the tolerance). Pods that aren't ready, or whose sample may include their startup, are left out of a scale-up; pods without metrics count against the direction of the change.

    *Chapter [56](../deployment/ch56-autoscaling.md)*

Threat model
:   A structured answer to four questions (the Threat Modeling Manifesto's): what are we working on, what can go wrong, what are we going to do about it, did we do a good enough job.

    *Chapter [35](../security/ch35-security-fundamentals.md)*

Three-way merge (template update)
:   Updating a generated project by merging the template's change (old version → new version) into the project, which keeps the project's own changes. Copier's `update` uses `git merge-file`; changes on the same lines conflict.

    *Chapter [72](../governance-org/ch72-platform-engineering.md)*

Throttling and retry modes
:   Cloud APIs limit request rates per account and per API. SDKs retry throttling and server errors with exponential backoff and jitter. A retry quota (a token bucket per client) stops retries when most calls fail; AWS's adaptive mode also limits the client's own send rate after throttling.

    *Chapter [59](../deployment/ch59-cloud-native-platforms.md)*

Thundering herd
:   Many clients acting at the same moment: reconnecting after a restart, retrying with the same backoff, refreshing the same cache entry, running a job at :00.

    *Chapter [42](../resilience/ch42-failure-modes.md)*

Time limiter
:   A timeout on a `Future` or `CompletionStage`. It stops *waiting*; whether the work stops is a separate question (§3).

    *Chapter [43](../resilience/ch43-resilience4j-deep-dive.md)*

Time to first token (TTFT)
:   With streaming, the delay before the first token arrives. Users perceive it as responsiveness; the rest of the answer arrives at the model's token rate.

    *Chapter [77](../governance-org/ch77-ai-native-microservices.md)*

Token bucket and GCRA
:   A bucket of *burst* tokens refilled at the limit's rate; each request takes one. The generic cell rate algorithm (GCRA) is the same thing with one number per key, the time the next request is "due", so it fits in a single Redis key and a few lines of Lua.

    *Chapter [40](../security/ch40-api-security.md)*

Token relay and token exchange
:   Relay forwards the user's token unchanged to the next service. Exchange (RFC 8693) trades it for a new token with one audience, fewer scopes, a shorter life and an `act` claim naming the service acting.

    *Chapter [36](../security/ch36-oauth2-oidc-jwt.md)*

Tolerant reader
:   A consumer reads only the fields it needs and ignores the rest, so the provider can add fields freely. It pairs with Postel's robustness principle: *be conservative in what you send, liberal in what you accept.*

    *Chapters [2](../foundations/ch02-characteristics-principles.md), [27](../communication/ch27-api-contracts.md)*

Topic, partition, key
:   A topic is a named stream; it is split into partitions for scale; the message key chooses the partition, and order is guaranteed only within a partition. Key by the entity (item id) to keep each entity's events in order.

    *Chapter [19](../architecture-patterns/ch19-event-driven-architecture.md)*

Topic (publish-subscribe)
:   Each message goes to every subscriber. In Kafka, every **consumer group** gets every message; within a group, each **partition** is read by one consumer.

    *Chapter [25](../communication/ch25-asynchronous-messaging.md)*

Traceability
:   Each fitness function names the decision it protects, and each decision names its functions, so a failure points at a "why" and a decision points at its evidence.

    *Chapter [73](../governance-org/ch73-adrs-fitness-functions.md)*

Trace context
:   The W3C `traceparent` header (trace id, parent span id, flags) that tracing systems propagate across HTTP and messaging hops.

    *Chapter [28](../communication/ch28-idempotency-correlation.md)*

Traces and spans
:   A trace is one request's path through the system; each span is one operation in it (a server handling a request, a client calling another service), with timings, attributes and its parent. They show *where* the time went.

    *Chapter [47](../observability/ch47-observability-fundamentals.md)*

Trace, span, span context
:   A trace is a tree of spans sharing a trace ID. A span is one operation with a start, an end, a kind (server, client, producer, consumer, internal), attributes, events, links and a status. Its span context (trace ID, span ID, flags, trace state) is what travels.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

Training run
:   The run that records what the AOT cache, the CDS archive or the native-image agent knows about. **What it didn't do, they don't know.**

    *Chapter [60](../deployment/ch60-native-images-startup.md)*

Transactional outbox
:   A table in the service's own database. The business change and the event row commit together, or neither does.

    *Chapter [15](../architecture-patterns/ch15-outbox-inbox-cdc.md)*

Trust domain and trust bundle
:   The authority that issues identities (`foodfleet.internal`), and the set of CA certificates that validate them. Federation adds other domains' bundles, each trusted only for its own domain.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

TTL and hit rate
:   Time-to-live bounds how long an entry lives; hit rate is the share of reads served by the cache. TTL bounds staleness only if nothing invalidates; it never prevents it.

    *Chapter [32](../data/ch32-caching-strategies.md)*

Two-phase commit (2PC)
:   Phase 1: the coordinator asks every participant to **prepare** (make the work durable and promise to commit if told). Phase 2: if all voted yes, it logs the decision and tells all to commit; otherwise to abort.

    *Chapter [30](../data/ch30-distributed-transactions.md)*

## U

Ubiquitous language
:   The vocabulary shared by domain experts and developers *within one context*, used in conversation, code, tests and APIs. If operations says "the kitchen rejected it", the code says `CancellationReason.RESTAURANT_REJECTED`, not `status = 7`.

    *Chapter [5](../foundations/ch05-domain-driven-design.md)*

Unit economics
:   Cost per unit of business: per 1,000 orders, per active restaurant, per delivery. It's the number that shows whether costs grow faster than the business.

    *Chapter [70](../performance-scalability/ch70-finops.md)*

Unit test
:   Tests one class or a few, in memory, with fakes for anything across a process boundary. Milliseconds each.

    *Chapters [61](../testing/ch61-test-strategy.md), [62](../testing/ch62-unit-slice-integration-tests.md)*

Upcaster
:   A function that converts an old version of an event into the current one when it's read; stored events are never rewritten.

    *Chapter [13](../architecture-patterns/ch13-cqrs-event-sourcing.md)*

Utilization
:   For a resource metric, the HPA divides pod CPU usage by the pods' CPU **requests**, not limits or node capacity. A target of 50% means "each pod should use about half of what it requested". Change the request and you change what the same load looks like.

    *Chapter [56](../deployment/ch56-autoscaling.md)*

Utilization and idle cost
:   Utilization is usage over capacity. Idle cost is what the cluster costs beyond what workloads use: unrequested capacity on nodes, plus requested capacity nobody uses.

    *Chapter [70](../performance-scalability/ch70-finops.md)*

## V

Versioning policy
:   When a change needs a new version (breaking changes only), how versions are named (FoodFleet: the `API-Version` header, not the URL), how long old ones live, and who approves exceptions.

    *Chapter [71](../governance-org/ch71-api-governance.md)*

VEX
:   A Vulnerability Exploitability eXchange statement: "this product is not affected by CVE-X because…". The machine-readable form of a waiver.

    *Chapter [41](../security/ch41-supply-chain-compliance.md)*

Virtual thread
:   A thread managed by the JVM, not the OS (Java 21, JEP 444). Blocking I/O unmounts it from its **carrier** platform thread, so millions can exist. Since Java 24 (JEP 491), `synchronized` no longer pins it to the carrier.

    *Chapter [8](../foundations/ch08-spring-boot-4-essentials.md)*

Volatility
:   Parnas's idea, sharpened by Löwy: isolate the things likely to change (pricing rules, payment providers, dispatch algorithms) behind stable interfaces, so change stays local. Useful **inside** a capability as well as between them.

    *Chapter [6](../foundations/ch06-service-decomposition.md)*

## W

W3C trace context
:   `traceparent: 00-<trace-id>-<parent-span-id>-<flags>`; the low flag bit is *sampled*. `tracestate` carries vendor-specific data.

    *Chapter [49](../observability/ch49-distributed-tracing-otel.md)*

WAF, CRS, anomaly scoring, paranoia level
:   A web application firewall inspects requests for generic attack signatures. The OWASP Core Rule Set adds up a score per request (5 for a critical match) and blocks at a threshold (5 by default). Paranoia levels 1–4 switch on progressively stricter rules: more detection, more false positives.

    *Chapter [40](../security/ch40-api-security.md)*

Warm-up
:   Running the request path before the service reports ready, so the JIT has compiled it when users arrive. It moves cost from the first requests to startup.

    *Chapter [60](../deployment/ch60-native-images-startup.md)*

WebSocket
:   An HTTP/1.1 `Upgrade` (or an HTTP/2 extended CONNECT) after which both sides exchange framed text or binary messages, plus ping/pong and close frames. Full duplex; no built-in reconnection or resume.

    *Chapter [26](../communication/ch26-websockets-sse.md)*

Workload identity
:   The identity of a running piece of software (this pod of order-service), as opposed to a user's identity. Proven with a key the workload holds, not with a network address.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

Workload identity and mTLS
:   Each workload gets a short-lived certificate whose URI SAN names it, such as `spiffe://foodfleet.local/ns/mesh/sa/gateway`. Both sides verify the other's certificate: encryption, and authentication of the caller. Authorization policies then refer to identities, not IPs.

    *Chapter [57](../deployment/ch57-service-mesh.md)*

Workload identity federation
:   The cluster is an OIDC issuer: it signs service account tokens and publishes its keys. The cloud trusts that issuer, and a role (AWS), managed identity (Azure) or service account (GCP) trusts one Kubernetes service account. Pods exchange a short projected token for short cloud credentials. EKS calls it IRSA (and, more simply, EKS Pod Identity), AKS and GKE call it Workload Identity.

    *Chapter [59](../deployment/ch59-cloud-native-platforms.md)*

Write-behind (write-back)
:   Writes go to the cache and are flushed to the database later, in batches. Fewer database writes; a crash loses what wasn't flushed.

    *Chapter [32](../data/ch32-caching-strategies.md)*

## X

X.509-SVID
:   A certificate carrying exactly one SPIFFE ID in a URI SAN, `cA=false`, `digitalSignature`, valid for minutes to hours.

    *Chapter [38](../security/ch38-service-to-service-security.md)*

XA / JTA
:   XA is the standard interface between a transaction manager and resources (databases, some message brokers); JTA is Java's API for it. Only resources that implement XA can take part: HTTP APIs, Kafka and most cloud services can't.

    *Chapter [30](../data/ch30-distributed-transactions.md)*
